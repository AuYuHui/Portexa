# Portexa 运行与验收规则

本文补充[产品方案](product-plan.md)中同步调度、SQLite 运维、可信服务器、归档和 Analytics 输入验收。这里的数值是实施默认值及验收目标，不代表已有运行结果；数据结构见[SQLite 数据模型](product-data-model.md)。

## 同步资源与优先级

采用单进程 Go Sync Engine，持有运行目录的排他锁，避免两个进程各自启动一套调度。使用进程内独立队列和 SQLite 调度记录，不引入消息队列服务。

| 资源或周期 | 默认规则 |
| --- | --- |
| Snapshot Worker | 独立10个 Fetch 名额，不借给历史任务；默认60秒，可在设置页选择30/60/120/300秒 |
| History Worker | 独立2个 Fetch 名额；近期检查默认5分钟，回填和修复在同一低优先级池轮转 |
| 全局连接上限 | 最多12个 Fetch，同时受账户互斥限制 |
| 同一账户 | 最多一个 Fetch，账户锁持有至结果提交或失败清理完成 |
| 调度扫描 | 每秒检查一次到期任务；每账户每类任务最多一个排队或执行记录 |
| 快照相位 | 按配置周期分配账户相位；完成后至少留27秒历史窗口，慢任务可顺延，不补发已错过的每个周期 |
| 历史准入 | 距该账户下一次快照至少25秒，且没有该账户待执行快照时才开始 |
| 历史 deadline | 不晚于开始后20秒，也不晚于下一次快照前5秒 |

12个名额是初始上限，不能绕过经纪商限制。以20个账户、每次耗尽20秒作粗略预算，快照独立10并发需要约40秒的批次时间；实际容量必须按连接、解码、数据库写入及调度延迟共同验收。

快照优先于近期历史，近期历史优先于回填。历史池按账户轮转，每次仅执行一个窗口，完成后释放名额和账户锁，不连续占有连接回填整个账户。

近期检查以已核验服务器自然日为固定窗口，反复检查更新同一窗口的核验时点，避免每5分钟新增一个几乎相同的覆盖区间。较早记录修订通过轮转修复或用户指定区间重查发现，不能承诺未重查区间的变化已被自动发现。

Snapshot Worker 使用不带历史选项的 `Fetch`。History Worker 仍调用现有带历史选项的 `Fetch`，其中附带的账户数据不替代快照路径的发布与时效状态，不假设 SDK 存在独立 History-only 接口。

### 任务合并与失败恢复

- 周期和手动刷新进入相同队列，接受账户 ID，不接受请求方临时指定地址；不绕过账户锁、固定接入点或资源配额。
- 同一任务尚未结束时，新 tick 合并为一次需求，不堆积每个错过的分钟。排队或执行状态由数据库唯一约束兜底。
- 历史因快照期限让位时保留区间，记录 `snapshot_deadline`，不当作凭据错误，也不因此延后快照。
- 连接断开、普通超时按60、120、300秒退避，上限300秒；快照和历史分别计算失败次数，历史失败不拉长快照重试间隔。
- `server_rejected` 不自动猜测错误原因，不连续重试；配置或凭据核对后由用户恢复。配置非法、只读声明缺失、协议不支持时暂停相应采集并显示分类。
- 资源超限或完整20秒预算仍无法完成的历史窗口二分，相邻窗口保留协议所需的边界重叠；让位造成的取消不触发二分。最小窗口为2个原始墙钟秒，仍失败则记录明确缺口，不标完整。
- 重启后将遗留运行标记为 `interrupted`，丢弃未发布修订，重建排队需求；只有已提交的覆盖和数据生效。
- 每次拨号前和结果提交前检查账户开关、接入点版本及凭据版本。过期任务不得跟随新地址自动迁移。

### 容量与隔离验收

使用20个合成账户、可控延迟的回环服务，分别覆盖正常返回、20秒超时、断线、历史大响应及 SQLite 写入压力。至少验证：

1. 快照与历史各自不突破配额，单账户 Fetch 并发始终为1。
2. 稳态快照的到期排队延迟 P95 不超过5秒；批量首次接入单独统计，不将其混作稳态结果。
3. 历史持续有任务时仍能取得进展，且不占用快照保留名额。
4. 历史能在该账户下一次快照前让位，失败窗口重新排队，旧成功数据保持可见。
5. 实测接近 SDK 资源上限时的内存、写入时间和队列延迟；达不到目标时降低刷新承诺并显示延迟，不用隐藏重试掩盖。

## SQLite 连接与事务

Go 数据库驱动选用 `modernc.org/sqlite`，通过其连接钩子、取消支持和在线备份能力接入；正式引入时锁定同时兼容 Go 1.26与 SQLite 生产基线的版本，启动时核对实际 `sqlite_version()`。

采用一个写连接和最多4个读连接。写连接先建立 WAL，随后建立只读连接；每个连接初始化并回读相关 PRAGMA，不能假设连接池新连接继承全部设置。

| 配置 | 默认值与执行位置 |
| --- | --- |
| `journal_mode` | 写连接初始化为 `WAL`，确认返回值 |
| `synchronous` | 写连接为 `FULL`，保护凭据、会话撤销和发布事务的持久性 |
| `foreign_keys` | 所有连接为 `ON` |
| `busy_timeout` | 1000毫秒，同时受请求上下文限制 |
| `wal_autocheckpoint` | 写连接为1000页 |

写队列优先处理会话撤销和快照提交，历史暂存、汇总、归档及清理使用低优先级。网络调用、图表计算、压缩和文件上传均在写事务之外进行。

历史暂存每批最多500行，清理每批最多1000行。事务持续时间目标 P95 不超过100毫秒，单次写入上下文上限1秒；超时回滚并拆小任务，不留下部分发布。当前订单版本切换和覆盖推进仍为一个原子事务，不能为了拆批提前暴露修订。

历史发布必须分别验收1,000、5,000、20,000条修订的首次发布与版本更新。开发机已发现20,000条版本更新略超100毫秒 P95，详见[本次测量](phase1-validation.md)。第二阶段先以每个独立完整覆盖区间约5,000条修订为规划预算，按实测继续调整。超出预算先细分覆盖区间、分别重新取得完整响应后独立原子发布；不把父区间的一部分暂存行提前发布。最小可分区间仍超预算时标记阻塞并验收专项方案。

读请求分批取数后及时关闭游标，不在慢速 HTTP 输出期间持有 SQLite 读事务。第一阶段仅开放有索引的采样时间、服务器开仓墙钟和订单号排序，不开放金额排序。历史按已确认时间、订单号做服务端分页；禁止将全部历史读入 Go 后进行金额排序分页。第二阶段若开放金额排序，须设计独立数值排序键，验证精度、范围、溢出及索引，不能使用金额 TEXT 字典序或转 REAL。

### ORM 与迁移边界

采用 GORM 负责对象映射、常规增删改查和分页；通过 `gorm.io/driver/sqlite` 的 `Conn` 注入既有 `database/sql` 连接池。SQLite 引擎、连接级 PRAGMA、写连接限制和 Online Backup 仍由 `modernc.org/sqlite` 与存储层管理，不因初始化 ORM 而另开一套默认连接池。

快照替换、历史版本发布、覆盖推进和会话撤销使用显式事务，事务内全部操作复用同一个事务句柄。批量写入和复杂查询可使用参数化 SQL；金额运算仍在 Go Decimal 执行，不由 ORM 转成 REAL 或隐式 SQL 算术。

表结构使用编号 SQL 迁移，应用启动检查迁移版本，生产不调用 `AutoMigrate` 自动改表。迁移覆盖 STRICT、复合外键、部分唯一索引、视图及触发器，并提供备份恢复路径；ORM 模型匹配已定义结构。

正式引入前验证 GORM、SQLite 适配器与底层驱动的版本组合，覆盖读写池归属、事务回滚、零值与 NULL、Decimal 精度及触发器效果。ORM SQL 日志不输出凭据、会话标识或敏感业务参数。

### Checkpoint 与备份

保留 SQLite 自动 checkpoint；每5分钟以低优先级执行一次 `PASSIVE` 检查并记录未完成页数。长读造成无法推进时关闭超时查询，延后回填；WAL 超过64 MiB仍持续增长时显示维护异常并暂停归档等重写任务。

`TRUNCATE` 只在明确维护窗口、读写任务排空后执行，忙时退出，不在在线请求中强制抢锁。不能直接删除 `-wal` 或 `-shm`；WAL checkpoint 也不能回收主库全部空闲页。

每日使用驱动支持的 SQLite Online Backup API 分步生成一致副本，不热复制一个仍在使用的 `.db` 文件。默认保留7份日备份和4份周备份，目标恢复点不超过24小时；备份失败不清理上一次有效副本。

备份覆盖数据库、归档清单和对应归档文件；凭据密钥单独备份并记录所需密钥 ID，不与数据库打包存放。异机副本加密并检查计数、摘要、`integrity_check` 和 `foreign_key_check`。异机存放位置在部署配置中指定，不由程序擅自外发。

恢复在停止主服务后进行，先验证副本，再恢复数据库、归档和匹配密钥。恢复后撤销全部旧会话，遗留执行标记中断，默认暂停采集；核对当前接入允许列表和配置后恢复调度。第一阶段用合成库完成备份、恢复和密钥不匹配验收。

## 快照容量与保留

20个账户每天每分钟各计划一次快照，为 `20 * 1440 = 28,800` 次计划；365天为10,512,000次。成功行数受失败、暂停和调度合并影响，不能把计划量当成已保存量，也不能仅凭行数判断 SQLite 性能。

| 数据 | 在线默认保留 | 规则 |
| --- | --- | --- |
| 原始资金分钟样本 | 最近90天，约259万条计划量 | 最新有效快照不因过期而删除；先归档、验证及备份，再删除旧行 |
| 小时汇总 | 最近730天 | 按 UTC 整点分桶，保存观测首末、极值、样本数、实际时间范围及缺口 |
| 日汇总 | 长期 | 按报告时区自然日分桶，记录时区和单位版本，不对小时或日金额简单取平均 |
| 当前持仓 | 只保留当前完整集合 | 与当前快照一起原子替换 |
| 历史交易、资金分类及修订 | 长期 | 不因快照降采样而清除 |
| 完成运行的诊断详情 | 30天 | 仍被数据、覆盖或归档审计引用的最小运行事实保留 |
| 过期或撤销会话 | 7天后清理 | 不影响当前会话或登录密码版本 |

小时和日汇总用于趋势展示，不足以恢复分钟路径，尤其不能把各账户在不同时刻发生的极值相加充当组合极值。保留粗粒度数据后不能继续声称拥有同范围的分钟最大回撤。

### 归档先于清理

超过90天的分钟数据按账户和时间段导出到私有压缩归档，保存原始金额、单位版本、采集窗口和必要来源元数据。清单记录格式版本、行数、起止范围、摘要及恢复校验状态。

文件写入临时位置，完成校验并原子发布后登记清单；副本备份确认后，才分批删除完全属于该归档的旧行。当前快照、尚需保留的来源引用和未解决数据不删除；失败时保留在线原始行，重试采用相同归档键避免重复清理。

归档不是有损降采样。较早范围需要精确重算、时间修正或资金重新分类时，读取或恢复对应原始归档；归档不可用则明确显示不可重算。没有完成并验收归档前，第一阶段不得仅因达到90天就自动删除样本。

归档不得在生产主库复制后删除 WAL，也不在每次清理后执行阻塞式全库 `VACUUM`。空间复用与维护窗口压缩分别处理，并以实际磁盘剩余量决定是否暂停低优先级写入。

## 可信 MT4 接入点

### 当前 SDK 的身份边界

当前 `Probe` 和 `Fetch` 均通过普通 TCP 建连，在读取服务器响应前发送 `InitialPacket`。该首包已经包含账号和密码派生材料；服务器显示名称的核对发生在后续认证流程。依据见 [client.go](../packages/mt4/client.go) 和 [handshake.go](../packages/mt4/internal/protocol/handshake.go)。

因此，正确的 IP、能解析的首响应和匹配的服务器名称均不等同于密码学服务端身份认证。`Probe` 也不是无凭据的接入点核验工具；网页 HTTPS 只保护浏览器到 Portexa，不改变 Portexa 到 MT4 的身份边界。

首版真实接入门槛已确定为“独立核验并锁定接入点，明确确认剩余风险后启用直连”。协议 SDK 保持冻结，产品不将当前直连描述为已提供密码学服务端身份认证。

拨号前必须同时满足：该接入点修订为 `reviewed`、证据完整、账户固定关系有效、该修订的 `risk_accepted_at_ms` 已记录，且账户采集已启用。任一门槛缺失即禁用该连接；选择产品门槛本身不为未登记的具体接入点生成核验或风险接受记录。

风险接受按接入点修订持久化，有效修订的正常自动采集和网络重连复用已有确认，不逐次询问。IP、端口或核验来源变化建立新修订，重新核验、确认并绑定，不能继承旧接受记录。风险接受不消除伪造接入点和路径劫持的剩余风险，也不能改写为密码学认证已通过。

### 登记与地址变更

1. 从经纪商独立官方渠道取得接入说明，或用无账户凭据的官方客户端服务器目录与独立官方渠道交叉核验。记录来源、核验时间、接入 IP、端口、显示名称及证据摘要；私有证据仅存私有目录。
2. 在发起任何 `Probe` 或 `Fetch` 前完成核验。第三方扫描结果、服务器自己返回的名称或一次成功认证不能独自作为信任依据。
3. 建立不可原地修改地址的 `server_endpoints` 修订。生产接入拒绝未经登记的目标和环回、链路本地、内网等非批准目标；测试回环仅由测试构造注入，不作为 HTTP 可开启的绕过参数。
4. 账户显式固定到已核验修订，调度只能从登记信息构造 SDK Config，不接受调用方临时传入目标，也不自动跟随服务端返回的其他接入点。
5. IP、端口或核验来源变化时建立新修订，暂停受影响连接并重新核验；不能因旧修订曾经通过就继承启用资格。提交旧配置结果前再次检查版本。

网络侧以目的 IP、端口出站允许列表和受控服务器环境减少误连；固定 IP 减少 DNS 误导，但这些控制不能消除路径劫持或证明对端密码学身份。界面和验收报告必须保留这一限制。

### 凭据密钥

采用 Go 标准库 AES-256-GCM，优先使用 `crypto/cipher.NewGCMWithRandomNonce` 生成并封装随机 nonce；按其每密钥消息上限管理使用次数。AAD 绑定账户 ID、稳定服务器 ID、接入点修订和凭据版本，防止密文被误用于其他账户或目标。

32字节加密密钥保存在数据库之外的本地密钥文件，文件权限0600、目录0700，数据库只保存密钥 ID。不得从系统登录密码派生此密钥；轮换先写入新密钥、验证重加密，再撤下旧密钥，期间保留可回退的旧副本。

第一阶段在密钥旁单独保存 `.usage` 计数，每次加密前持久化预留一次使用量，数据库回滚不回退计数，达到每密钥2^32次时拒绝继续加密。该文件与密钥一起独立保管；恢复不能降低已知使用计数，计数缺失或损坏时停止使用，不自动重建。第一阶段没有自动密钥轮换入口。

更换固定接入点必须经过核验，再明确重绑定和重加密，不能悄悄将原凭据发送到新地址。密钥缺失、版本不符或认证标签失败时停止受影响采集，保留原密文和历史数据，不自动生成新密钥覆盖。

### 接入验收

- 未登记、未核验、未记录剩余风险接受、已撤销、跨服务器绑定及被修改的接入点均不能触发 SDK 发送首包。
- 合成伪造服务器即使返回同名配置，也不能获得可信登记或绕过启用门槛。
- 记录与界面不把名称一致、认证成功或投资者声明描述为密码学身份认证。
- 错误密钥、错误 AAD、密文篡改及接入点版本变化不触发带旧凭据的连接。
- 运行中变更目标或凭据时取消旧任务，旧结果不得发布为新配置的有效结果。
- 已核验并确认风险的同一修订可以自动采集与重连；新修订必须重新满足门槛，不能因旧修订成功而自动放行。

## 跨账户时间与资金验收

WP2 原始资产曲线已按下述90秒采样限制实现，具体契约见[资产走势](asset-trends.md)。原始估值只依据成功快照与单位版本，交易历史覆盖和资金对账仍是后续收益指标的额外门槛。

### 最近已知合计与分析输入

总览默认称“最近已知合计”，即使各账户均未过期，也显示纳入数量、最早采集开始与最晚采集完成时间；不能把不同账户的数值称为同一时刻精确估值。

分析采样点按 UTC 每分钟对齐，每户只选择该点之前完成的最近有效快照。初始验收上限为：样本完成时间距该点不超过90秒，所选采集窗口的并集跨度不超过90秒，且满足历史覆盖和资金对账要求。

不满足任一条件时，该分析点留空；不得用总览的过期旧值补成有效收益点。符合条件的结果仍注明估算及实际采集范围，不承诺同报价时刻。资金事件落在采集不确定窗口、无法判断是否计入边界权益时，等待后续可对账样本。

归档后的图表注明分钟、小时或日分辨率。最大回撤、收益率复核使用所声明分辨率的原始样本或已恢复归档，不能将粗曲线推算的结果标为分钟指标。

### 时区与分类

| 验收输入 | 预期行为 |
| --- | --- |
| 服务器偏移已知，历史规则未知 | 当前时间可解释；未知历史区间不进入依赖准确日期的统计 |
| 夏令时切换造成重复墙钟 | 保留原值并标记歧义，直到有证据确定唯一 UTC |
| 夏令时跳过的不存在墙钟 | 标记无效时间，不自动平移到下一小时 |
| 修改时区规则 | 追加版本，重新解释原始时间，失效并重算受影响报告 |
| 余额记录为正 | 仍不能直接判为入金，可能为返佣或分成收入 |
| 跟单分成支出、返佣、外部提现 | 分别按成本、收益、资本流出处理，保留人工理由与修订 |
| 订单金额或时间发生修订 | 原值保留，相关分类和分析重新校验，不能继续使用旧有效标记 |
| 两笔内部转账金额、单位或期间不匹配 | 保留待核对和在途状态，不自动抵消 |
| 小时或日归档缺失 | 说明覆盖与原始归档可用情况，不生成完整分钟回撤 |

## 实施与发布边界

第一阶段进入编码前，先用模型原型验证键、外键、发布回滚、会话撤销和配置版本检查，再固化 API 与页面契约。数据库字段、索引和本页资源默认值作为实现依据，不再笼统留给编码时临场决定。

上线验收覆盖实际 Go 驱动的 SQLite 版本、WAL、并发、备份恢复和密钥隔离；内存原型验证不能替代这些检查。引入旧数据库时先做可恢复备份，迁移失败恢复副本，不自动执行破坏性降级。

修改后执行 `make check`，协议独立测试保持 `GOWORK=off`。普通验证只使用合成数据和回环服务，真实接入的风险选择不构成自动登录真实服务的授权。
