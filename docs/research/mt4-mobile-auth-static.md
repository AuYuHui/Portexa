# MT4 移动客户端认证调用链：静态研究

核验日期：2026-11-11。研究对象：MetaQuotes `MetaTrader4Terminal` 4.0.1478 / build 5048，arm64，iOS-on-Mac 可执行文件。SHA-256：`8a8e4693f10e13f450fb69999af110f006b26d3d4a142962e83ffbab5b7feb7a`。

## 结论与边界

已从实际程序定位交易服务器登录 UI、账号配置、28 字节首段、服务端挑战处理、后续认证记录、记录加解密及账户/订单接收链。主任务随后回传：新生成的纯Go会话已在两个目标通过配置结构/非空服务器名前缀验证，并在一个目标以公开移动端兼容元数据组完成账户结构、当前订单及指定时间段历史的读取。该回传支持原生路线可行，尚未等于全部字段与官方UI逐项一致、所有平台/build兼容或完整账户聚合产品已完成；原始证据和边界见V6–V9。首段包含账号与密码摘要的变体，不能称作匿名hello；重放该首段仍属于发送认证相关材料。[B1–B9, V6–V9]

本研究仅阅读程序静态代码和静态元数据，未读取应用用户数据、真实账号密码、抓包或业务 payload，未启动或附加实际客户端进程、改签或更改系统配置。文中注明的合成向量实验只在隔离的 Unicorn 内执行已定位函数，未与真实进程或网络连接交互。此文件不收录任何真实协议样本、端点、安装标识或凭据。文中变量名均为分析命名，地址均为未加 ASLR slide 的静态虚拟地址。[M1]

证据分级：函数调用、访存布局和分支属于**静态已确认**；“挑战”“认证子记录”“设备信息”等是根据输入/输出和调用位置作的**语义解释**，不是厂商发布的字段名称；服务器兼容性、认证完成及账户读取属于**待实际验证**。MD5/AES 的初始命名来自实现结构与一手标准对照；主任务后续对 AES 和两条不同摘要路径分别做了合成向量离线仿真，证据见 V2–V4。

主任务另行回传的离线复核：两组已授权连接样本的完整 C28 与独立生成结果逐字节一致；按本报告的连续流方向解码首响应后，版本字段都得到 1470。该结果支持首段生成和初始流层方向，不证明挑战派生、后续记录或完整认证已正确。此子任务未访问这些样本，报告不收录其材料。[V1：主任务本次会话的离线验证回传]

## 1. 确认属于交易服务器登录链

`InitServer:Login:` 经全局 core 的 `+0x45c0` 服务器对象查询，把服务器结构 `+0x3ac` 的 16 字节复制到 `CViewLogin.m_hash`。`Connect` 读取登录与密码文本框、该服务器 hash、开关和可选 OTP，调用 `0x1000341ec`；后者用 `0x100037a38` 更新 core `+0x48` 的账户配置。[B1]

网络循环 `0x100038904` 调用 `0x10003493c → 0x100037730` 复制这个 core `+0x48` 配置，再调用 `0x100038654 → 0x10003bfb4 → 0x10003c3fc`。因此本研究链条与交易服务器选择及账户登录字段有直接数据流关系，依据并非仅为报文长度或某个 crypto 函数的存在。首段函数也被其他连接路径复用，不能把它的所有调用者一概命名为主交易连接。[B1–B2]

两项容易误读的证据：[B1–B2]

- `0x100033d30` 使用文件管理器、目录创建与文件移动；它是本地路径准备，不能称为启动网络连接。
- `0x100038654` 返回 0 后的静态日志模板是“账号占位符: login”。该日志本身不构成服务端完成认证的证据。

## 2. UI 密码先经过本地配置保护

`0x1000287e8` 将密码 UTF-8 字节复制至配置的 16 字节字段，再以安装相关派生 key 进行反馈编码；`0x1000286c4` 执行逆变换并构造临时字符串。安装相关派生链引用本地安装字符串、账号及静态盐值；本研究没有读取其实际存储或标识。getter 把临时缓冲区最后一字节置零，故只能确认此字段/路径的处理方式，不能据此推导所有版本和协议的密码长度规则。[B3]

字节 key 的反馈编码原语（`0x1000268a8`）可表达为：`prev=0`，`C[i]=P[i] XOR ((key[i mod keylen]+prev) mod 256)`，之后 `prev=C[i]`。逆函数 `0x10002693c` 用原密文的上一字节恢复。它同时在若干协议记录中复用；本地密码保护的安装相关派生步骤不能直接当作网络会话 key 派生。[B3, B6]

## 3. 28 字节首段的生成规则

正常登录分支 `0x10003c3fc` 先调用配置密码 getter，要求账号非零、密码非空；以 getter 返回的 UTF-8 字节计算标准初始化的 MD5，结果 `h[16]` 存入连接对象 `+0x25`。MD5 的 IV、轮常量和填充流程与 RFC 1321 对应。程序还存在特殊连接 mode 的静态字符串分支，不应推广到普通账户登录。[B2–B3；MD5 对照：[RFC 1321](https://www.rfc-editor.org/rfc/rfc1321)]

在最后一层混淆之前，布局为：[B2]

| 首段偏移 | 长度 | 生成内容 |
|---|---:|---|
| 0 | 1 | 普通 mode 为 0；连接 mode==1 时为 11 |
| 1 | 1 | `(198 + byte0 + low8(login) + flag) mod 256` |
| 2 | 1 | 常量 10 |
| 3 | 16 | `h[i] XOR ((h[i] + (i==0 ? 0 : h[i-1])) mod 256)`，后一项使用原始摘要 |
| 19 | 4 | login，uint32 little-endian |
| 23 | 2 | 常量 400，uint16 little-endian；其官方语义未确定 |
| 25 | 2 | 常量 1478，uint16 little-endian；与客户端版本对应 |
| 27 | 1 | `flag = (连接 mode==2)` |

随后仅对偏移 1..27 调用 `0x1000267bc`，使用静态 16 项 uint32 表的低字节执行反馈混淆；偏移 0 不变。最终通过 `0x10003717c` 发送 28 字节，再进入 `0x10013c95c`。首段的密码派生字段和账号均可与已授权样本离线精确比较，但发送成功不等于完整登录成功。[B2, B6]

## 4. 初始服务端响应及挑战处理

`0x10013c95c` 先用 `0x100037688` 读取 1 字节返回值，仅对普通 0 或指定可选认证状态继续。随后经 `0x100037378` 分段读取额外 1 字节、2 字节版本、4 字节字段和 64 字节挑战。**这些后续字段先经过一层连续流解码，不能直接按 TCP 密文字节解释。** 偏移以下表原始字节流起点计，表中用途指解码后的值。[B4, B6]

| 流偏移 | 长度 | 去向/用途（除首状态外均需先流解码） |
|---|---:|---|
| 0 | 1 | 初始状态；读失败时 helper 返回合成错误码 |
| 1 | 1 | 额外字节，业务语义待确认 |
| 2 | 2 | 连接对象 `+0x72`；版本阈值检查、交换字节序 |
| 4 | 4 | 连接对象 `+0x74`；后续 PRNG seed 与摘要输入 |
| 8 | 64 | 后续 key/挑战变换输入 |
| 72 起 | 可变 | 由 `0x10013d2b4` 继续读取 8 字节头与主体 |

初始状态不是完整会话认证结果。版本阈值检查与特殊 mode 可能提前返回；不能把所有流都强套为 72 字节前缀加同一种认证流程。[B4]

`0x10013c95c` 在读取额外字节前清零连接 `+0x48..+0x57` 的双向流状态。`0x100037378` 先调用原始读取，再以连接 `+0x25` 的 16 字节 key 解码：`P[i] = C[i] XOR ((key[counter mod 16] + prevPlain) mod 256)`，随后 `prevPlain=P[i]`、`counter++`。此时 key 是原始密码 MD5；接收状态在连接 `+0x48/+0x4c`，跨所有读取调用连续保留，包括 `0x10013d2b4` 的头与主体。首个 status 由原始读取 helper 取得，未过该流层。[B3–B4, B6]

对应发送 helper `0x1000373ec` 使用独立 `+0x50/+0x54` 状态，同样以上一**明文**字节作反馈。它与前述以上一**密文**字节作反馈的 `0x1000268a8` 是两个不同原语。C28 和后续 `0x18` 请求直接走原始写入；command `0x10` 等才走此连续流编码。`0x10013c95c` 后段会将挑战派生 key 写回 `+0x25`，尚未看到它在此时重新清零接收状态；后续样本验证必须保留计数器和反馈状态，并按代码时点切换 key。[B4–B7]


工作 key 最初复制自连接 `+0x25` 的原始密码 MD5。程序依次执行静态表反馈混淆、部分字节取反、64 字节区块重排，随后按 4 字节字段是否为零分支。非零路径的分支 seed 为 `login + ((LE32(field4) >> 8) & 255) + 10`（32 位环绕）；4 次生成随机数，各取低 3 位选择表中一个算子，算子输入包含连接、该字段、64 字节块和 16 字节工作 key。[B4]

| 表序号 | 函数地址 |
|---:|---|
| 0 | `0x10013cf58` |
| 1 | `0x10013cfbc` |
| 2 | `0x10013cfcc` |
| 3 | `0x10013d074` |
| 4 | `0x10013d11c` |
| 5 | `0x10013d12c` |
| 6 | `0x10013d14c` |
| 7 | `0x10013d228` |

上述表在 `0x100259af8`，每项 16 字节且本版本第二个 8 字节为 0。零字段分支不调这 8 个算子：对 key 调 `0x1000267bc`，再调接受 **16 个 uint32 元素**的 `0x100026808`，再反转 16 字节并交换相邻字节。不要把 `0x100026808` 的 uint32 表参数误写成 `0x1000268a8` 的 byte key。[B4, B6]

### 4.1 非零字段分支：算子输入可消去前置混淆

这里定义 `B` 为 `0x10013ca88` 调用 `0x100037378` **流解码后**写入 `sp+0x20` 的 64 字节，`h` 为连接 `+0x25` 的原始密码 MD5；`E` 表示仅对偶数索引字节取反，`S` 表示相邻字节交换，`N` 表示全部取反，`R` 表示反转完整 64 字节。沿非零字段分支，各步如下。[B4]

| 指令区间/关键地址 | 对 64 字节块的操作 | 其他状态 |
|---|---|---|
| `0x10013ca64..0x10013ca74` | 尚未读取 B | 连接 `+0x74` 的 4 字节字段做第一次 byte reversal |
| `0x10013ca88` | 从流解码读取 B | 接收流状态继续累计 |
| `0x10013ca94..0x10013caa8` | `E`：索引 0、2、…、62 取反 | — |
| `0x10013cab4..0x10013cad0` | `S`：每 2 字节交换 | 使用 `rev16.16b` |
| `0x10013cadc..0x10013caf0` | `N`：全部 64 字节取反 | — |
| `0x10013cb00..0x10013cb28` | `R`：完整反转 64 字节 | 两次 16 字节对换，每个 16 字节内部先 reverse64 + ext8 |
| `0x10013cb34..0x10013cb68` | 不改块 | 复制 h 到 `sp+0x10`，用静态表 `T@0x10021bf40` 做反馈编码 |
| `0x10013cb78..0x10013cba0` | 再做 `R` | 抵消第一次 R |
| `0x10013cbac..0x10013cbc0` | 不改块 | 工作 key 的奇数索引取反 |
| `0x10013cbc4..0x10013cbd4` | 不改块 | 4 字节字段做第二次 byte reversal，并将结果放入 w8；据此分零/非零 |
| `0x10013cbec..0x10013cc00` | 不改块 | 工作 key 奇数索引再次取反，抵消上一步同类操作 |
| `0x10013cc0c..0x10013cc20` | 再做 `N` | — |
| `0x10013cc2c..0x10013cc48` | 再做 `S` | — |
| `0x10013cc50..0x10013cca8` | 不改块 | SIMD 并行恢复工作 key，详见下文 |
| `0x10013ccb0..0x10013ccc4` | 再做 `E` | — |
| `0x10013ccc8..0x10013cd04` | 算子接收上述最终块 | 计算 seed、取表项，设置 x0/x1/x2/x3 并调用 |

因此，64 字节操作顺序为 `E → S → N → R → R → N → S → E`。每个操作为自身的逆，且对应操作按嵌套次序相消，**进入第一个算子时的 transformed64 恰好等于 B**。这是对本版本非零分支的代数消除，并不是忽略前置代码。零字段分支停在共同前段，其块仍为 `N(S(E(B)))`，每对字节是 `(~B[2j+1], B[2j])`，不能套用恒等结论。[B4]

key 的前置段同样可消去：反馈编码先得到 `C[i] = h[i] XOR ((T[i]+(i==0 ? 0 : C[i-1])) mod 256)`；两次奇数索引取反相消。SIMD 步骤使用**并行变换前的原 C 数组**，构造前一 C 字节，再计算 `C[i] XOR ((T[i]+(i==0 ? 0 : C[i-1])) mod 256)`，所以恢复出 h。这里不能用迭代恢复后的上一 h 字节替代上一 C 字节。[B4]

本次另用 256 组合成索引块/合成摘要建立指令对应模型，分别验证 64 字节变换恒等、key 恢复恒等、两次 4 字节 reversal 恒等，全部成立。该检查没有执行厂商程序，也没有读取真实样本；它验证转写的代数关系，不代替 root 后续对捕获样本的验证。[M2：本次合成模型检查]

### 4.2 x1、seed 与 x2/x3 的精确阶段

令 `f[4]` 为流解码后存入连接 `+0x74` 的四个字节，`F=LE32(f)`。第一次 SIMD `zip1.8b → rev64.4h → uzp1.8b` 等价于 `bswap32(F)`；第二次同样操作恢复 F。`0x10013cbd8` 将第二次操作结果放入 w8；之后到 seed 计算前没有改写 w8 的指令。seed 因此为 `(login + ((F >> 8) & 255) + 10) mod 2^32`，取的是**恢复原序之后**的字段，不是中间的 `bswap32(F)`。[B4]

每次算子调用前，`0x10013ccf4` 都重新执行 `ldr w1,[conn,+0x74]`。参数规范化为 `x0=conn`，`w1=F`（即 x1 低 32 位、上 32 位清零），`x2=&B[0]`，`x3=&workingKey[0]`；第一次调用时 `workingKey=h`。复核本版本 8 个算子后，未见它们写入 B 或连接 `+0x74`：它们只读取该块/字段并演化工作 key，或写入连接临时数据缓冲区。因此四次调用的 B/F 内容保持不变，key 逐次演化；不能每次都重置回 h。[B4]

算子 6/7 调用 `0x1001427a8`。主任务用 Unicorn 对该函数执行 1/16/64/97 字节**合成输入**并比对，回传其符合 SHA-1 压缩轮，但以 little-endian 装载消息词、仅补零至 64 字节边界、不加标准 `0x80` 与 bit-length 尾部，5 个状态字也按 little-endian 输出，调用者取前 16 字节。因此不能替换成标准 `SHA1(data)`。此验证不涉及真实账户样本；它与下文经独立合成向量核验的完整标准 SHA-1 包装是两条不同调用方式，不能混用。[V2：主任务本次合成向量仿真回传]

PRNG 的 seed 函数范围为 `0x1000269d4..0x100026aa8`，next 为 `0x100026aa8..0x100026be4`。静态递推为 `state = state * 214013 + 2531011 mod 2^32`，输出 `(state >> 16) & 0x7fff`；状态与线程环境有关。端序处理必须按指令顺序复核：4 字节字段在本路径有两次 byte reversal，不能只看到第一次就把最终 seed 误当作 big-endian。[B4]

### 4.3 type9 不是普通 hash：可归约为小型 uint64 解释器

`0x100066890` 将32字节上下文的四个 uint64 清零；`0x1000668a4..0x1000854a0` 消费 uint64 数组。后者约31,487条 arm64 指令、无外部调用或间接跳转，包含大量 NAND、AND/OR、加减展开。两张64项静态表 `0x1002aa860/0x1002aaa60` 的逐项 XOR 是 `1<<i`，辅助按 bit 重建简单运算；不能据函数体长度把它命名为某种标准 hash。[B4；追加静态来源：上述函数/表]

结合控制流、上下文写入点和纯合成数组的离线执行，可规范为以下最小语义。上下文依次为 `acc / pc / A / B`，初始 `acc=0` 由调用者执行 init；每个 type9 块单独 init。函数内部对长度>=3的数组把 pc置0，按每3个 little-endian uint64 为一条指令消费：[B4, M3]

| 规则/归一化 opcode | 语义 |
|---|---|
| `opcode=(word[pc]>>21)&0xff` | 指令字的 bit21..28，其他位不参与已确认分派 |
| `0xd8` | 立即返回当前acc，并只清零上下文acc；不装本条A/B、不前移pc |
| 其余 opcode | `A=word[pc+1]`；若 `(A>>21)&0xff==0xf5`，改用当前acc；`B=word[pc+2]`始终作为字面值 |
| `0xab` | `acc=A+B`，uint64环绕 |
| `0xa9` | `acc=A-B`，uint64环绕 |
| `0x54` | `acc=A AND B` |
| `0x70` | `acc=A OR B` |
| `0x91` | `acc=A XOR B` |
| `0xb1` | `acc=A << (B % 24)`，uint64环绕 |
| `0xc8` | `acc=A >> (B % 24)`，逻辑右移 |
| 未识别 opcode | 保持acc；仍装载/归一化A、装载B并前移pc |
| 正常轮末 | `pc+=3`；还有完整3词则继续，否则返回acc并保留它 |

少于3词或空指针直接返回0，不改上下文；尾部1/2词忽略，即使其中首词编码为HALT。HALT仅清acc，保留当前pc和上一轮A/B；曾观察到首次HALT后整个上下文为0，是因为其余字段原本为0，不能概括为它清除32字节。调用者把 type9 payload 长度右移3位作为词数，VM本身再按3词循环。[B4, M3]

**[M3] 本轮离线合成验证**：使用主任务已有的 `emulate_core.Core` 和固定安装映像，在 Unicorn 2.1.4 私有映射中执行，未附加真实进程、未读取任何真实 type9 数据。验证包括：64个单bit指令字确认opcode位域；256个opcode枚举；7种运算的随机64位单指令；20组移位边界（含23/24/25、63/64/65、UINT64_MAX）；A引用/相同B标记仍为字面值；HALT、unknown和尾部词数；另6组组合程序同时覆盖全部运算、随机无关位、A引用和尾部情况，**返回值及四字段上下文均逐字节匹配上述紧凑模型**。组合程序的原始MBA执行曾触及20M指令预算；提高到100M后，6组均完成，未将预算中断计作通过。

主任务随后回传：该紧凑模型与两个目标平台真实样本的 type10 完全匹配（包含下节F符号扩展），无需以封闭厂商映像作为运行依赖。该子任务未读取真实样本。[V5：主任务实际样本离线对照回传] 这证明该短语义已通过目标连接中 type9→type10 的一致性检查。Unicorn 加载厂商映像只是研究判据，不能作为“完全开源 Go”最终运行依赖。[M3]

### 4.4 type9 返回值到 type10：注意 int32 符号扩展

`0x10013d440..0x10013d454` 从 VM 返回值 V 派生连接 `+0x78`：先用 `ldrsw` 把服务端 F 按 **int32 符号扩展**到64位，再与 `uint64(login)<<32` 按位或，得到 `mix`，最后异或一个静态64位常量 C。`0x10013e66c` 生成 type10 时再次异或同一 C，因此 type10 解码后的8字节主体可以直接表达为 `LE64(V XOR mix)`。[B4–B5]

其中 `mix=(uint64(login)<<32) OR uint64(int64(int32(F)))`。F高位为1时，上32位会被符号扩展部分OR成全1，不能默默改成对F零扩展。此为本版本 arm64 指令的精确转写；该异常格式是否在其他客户端版本相同仍待核验。[B4–B5]

## 5. 普通后续请求：0x18 与子记录

首响应记录解析成功后，普通路径进入 `0x10013d974`，继续构造并发送请求；这不是仅返回“已登录”。流程如下。[B5]

1. 用 `login + LE32(field4)` 重新 seed PRNG，取 64 次 next 的低字节形成 `r[64]`。
2. `0x10013e134` 计算 `MD5(0x0a || 程序静态10字节常量 || LE16(1478) || 现工作key16 || r64 || LE32(login))`，作为新工作 key；同时保存副本用作外层 key。
3. 从表 `0x100259b78` 复制 9 个函数项，令 `n=5+(next()%4)`，只对前 n 项进行 128 次随机交换，然后依序生成前 n 个子记录。故本版本普通路径的 n 为 5..8，第 9 项不会进入该次前缀。
4. 加首字节 `0x18`，外层记录设置 type=2、mode=1，以步骤 2 保存的 key 编码；通过 `0x1000370a0` 发送。函数返回发送结果，**没有读取服务端确认**。

| 表项 | 函数 | 子记录与工作 key 影响 |
|---|---|---|
| 0 | `0x10013e228` | type0，mode1，60 或 68 字节；读取设备/安装相关信息，仅分析其代码，未读取实际值 |
| 1 | `0x10013e4b4` | type1，mode0，20 字节摘要；派生连接 `+0x80` 的 16 字节材料 |
| 2 | `0x10013e66c` | type10，mode0，8 字节，来自连接 `+0x78` 与静态常量的异或 |
| 3、5、7 | `0x10013e6d8` | type3，8..39 字节 PRNG 填充；编码后用该填充作为 byte key 更新工作 key |
| 4、6、8 | `0x10013e7b0` | type4，8..39 字节 PRNG 填充；不执行上述工作 key 更新 |

这不是将同一个 key 独立用于所有内层记录。type3 会影响后续子记录的 key，必须按实际洗牌顺序递推；外层 key 则使用子记录生成前的副本。[B5]

type1 使用完整标准 SHA-1 包装 `0x100141490 / 0x1001426ac / 0x1001426f8`：主任务用原函数链对长度 0/1/16/64/97/128 的 6 组合成消息离线仿真，全部逐字节匹配标准 SHA-1 的 20 字节结果。它执行标准消息装载、padding 和大端结果输出；不可与算子6/7的 raw little-endian-word、仅补零压缩路径互换。[V3：主任务合成向量仿真回传；算法标准：[FIPS 180-4](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)]

### 5.1 完整发送布局与随机数消费顺序

令 `Kc` 为完成挑战算子并最终存回连接 `+0x25` 的 16 字节，`F` 为恢复原序的服务端 4 字节字段。重新 seed 为 `(login+F) mod 2^32`。64 次 next 各取低 8 位形成 `r64`；它只参加 key 派生，**没有作为独立 64 字节字段发送**。外层 key 为 `K0=MD5(0x0a || Q10 || LE16(1478) || Kc || r64 || LE32(login))`，其中 Q10 是程序 `0x100242b98` 开始的 10 字节静态常量。初始化 mutable 内层工作 key `W=K0`，另保存不可变外层副本 K0。[B5]

该函数的 raw TCP 写入字节顺序为：`0x18 || header8 || encodedPayload`。其中 `header8=LE16(innerConcat.length) || LE16(2) || LE16(1) || LE16(random)`，header 不执行额外反馈编码；主体是所有已编码子记录的拼接，再以 K0 做 mode1 编码。mode1 的整块前缀为 AES-CBC 零 IV，非整块尾部独立执行反馈编码。此请求直接调用原始写入，不再包一层 `0x1000373ec` 连续流编码。[B5–B6]

| PRNG 阶段 | 规范顺序 |
|---|---|
| 第 1..64 次 | `r64[i]=low8(next())` |
| 第 65 次 | `n=5+(next()%4)` |
| 第 66..321 次 | 128 轮交换；每轮先取 `a=next()%n`、再 `b=next()%n`，交换表前 n 项中的 a/b |
| 每个 type0/1/10 子记录 | 各取 1 次 next 作其 header 的 uint16 随机字段 |
| 每个 type3/4 子记录 | 先取 next 决定 `length=8+(next()%32)`，再取 next 作 header 随机字段，随后每个 payload 字节再取 1 次 next 的低 8 位 |
| 全部子记录后 | 再取 1 次 next 作外层 header 随机字段 |

表的前 5 项固定包含 type0、type1、type10、type3、type4；n=6/7/8 时依次多包含 type3/type4/type3，然后只洗牌前 n 项。type3 的 key 演化在它自己的记录完成编码后执行，影响后续记录。各次 header/body 的 `0x1000268a8` 调用都独立从反馈 prev=0 开始，不能把它误作跨记录持续流状态。[B5–B6]

### 5.2 type0 的结构和可替代范围

`0x10013e228` 的 payload 布局如下，偏移相对解码后的 type0 主体。源代码路径包含本地安装、消息设置、应用映像大小和推广来源信息，不能把这 60/68 字节全部称为硬件指纹。[B5]

| 主体偏移 | 长度 | 静态生成规则 |
|---|---:|---|
| 0 | 16 | 安装材料 I，由 `0x100023aac` 取得；最后重算 `I[0]=sum(I[1..15]) mod 256` |
| 16 | 4 | `BE32(message_idn)`，值来自设置 getter；该字段本身没有在此处套反馈编码 |
| 20 | 4 | 对 `LE32(__TEXT.vmsize/1024)` 调静态表反馈编码 `0x1000267bc` |
| 24 | 4 | 对四个零调同一个静态表反馈编码 |
| 28 | 32 | `utm_campaign` 的编码转换后字符串，最多拷贝32字节并强制最后一字节为0；空字符串分支为32个零 |
| 60 | 8（可选） | 服务端版本>=1295时存在：`LE64(uniqueUserNumber>=10000 ? uniqueUserNumber : 0)` |

映像大小来源已追至 `0x100017028 → 0x10015bac8`：遍历当前 Mach-O 的 `__TEXT` segment，取 `segment_command_64.vmsize` 低32位，与1478异或存入全局对象 `+0x800`；type0再异或1478还原并除以1024。本研究对象 `__TEXT.vmsize=0x254000`，故该字段编码前为2384。它不是系统版本或运行内存大小。[B5；追加静态来源：上述两函数；segment结构：[Apple loader.h](https://github.com/apple-oss-distributions/xnu/blob/main/EXTERNAL_HEADERS/mach-o/loader.h)]

I 的客户端源头 `0x100023034/0x1000237f4` 可从本地保存值取得，缺少时用 `CFUUIDCreate/CFUUIDGetUUIDBytes` 生成，失败时还存在基于随机输入 MD5 的 fallback；随后经字符串转换、缓存/存储路径，再由 `0x100023aac` 导出16字节并重算首字节校验。这里没有向服务器领取 I 的调用。`uniqueUserNumber` 也存在客户端 UUID/时间/随机数生成分支；本研究没有读取任何实际安装值。[B3, B5；追加静态来源：`0x1000237f4`、`0x100023aac`、`0x10002ba7c`、`0x10002bc24`]

据此可以为 PoC 提出**待验证的本地候选规则**：生成自己的持久化安装材料 I、重算首字节校验，并在 type0 与 type1 一致使用；空推广来源使用客户端已有的全零分支。此规则复现客户端自身的数据依赖，**没有证明服务器允许替换 I、允许省略/置零其他字段或接受任意映像大小/uniqueUserNumber**。不能把客户端生成逻辑提升为服务端兼容性承诺。[B5]

### 5.3 type1 摘要和连接 +0x80 的长度

令 `W` 为执行到 type1 时的 mutable 工作 key（受此前 type3 影响），I 为 type0 使用的同一安装16字节。标准 SHA-1 计算：[B5, V3]

- `D1=SHA1(I || LE32(login) || Kc || W)`，20字节；
- 先复制 W 的16字节到连接 `+0x80`，再就地执行 `FE(key=D1,length20)`、`FE(key=I,length16)`；两次都只处理16字节内容，反馈状态各自重置；
- `D2=SHA1(LE32(login) || Kc || LE32(F))`，20字节，作为 type1 主体；其记录为 type1/mode0，编码 key 是当时的 W；W 自身不因 type1 改变。

因此连接 `+0x80` 保存的是**16字节材料**，并非20字节。指令 `0x10013e554` 只写一个 q0，后续两次编码也明确传入数据长度16。20字节分别是 D1 和 type1 主体 D2；`0x100037378/0x1000373ec` 不读取连接 `+0x80`，不能把它当作这些 helper 的直接流 key。[B5–B6]

### 5.4 后续连续流的 key 与状态

| 阶段/方向 | key | 反馈与计数器 |
|---|---|---|
| 初始 raw status 后的服务端首响应 | 原始 `MD5(password)`，位于连接 `+0x25` | RX `+0x48=prevPlain`、`+0x4c=counter`，从0开始 |
| 首响应处理结束后 | `0x10013cea8` 写回的 Kc | 保留已经累计的 RX prev/counter；未见此处重置 |
| C28、0x18 原始写入 | 不调用连续流 helper | 不消耗 TX prev/counter |
| command0x10及之后的连续流写入 | Kc，仍从连接 `+0x25` 读取 | TX `+0x50=prevPlain`、`+0x54=counter/index`，与RX独立；首个此类请求起点仍为0 |

prevPlain 的“明文”仅指**连续流层解码输出**：初始记录的 payload 在这一层之后仍可能是 AES 密文。对 payload 做 AES 解密不会改写连接 RX 状态。首个 raw status 不计入流层，之后的头、主体都累计，不能仅按 read 调用次数或 AES 明文长度计数。[B4–B7]

## 6. 记录头、反馈编码与块模式

`0x10013dccc` 编码、`0x10013dbc4` 解码的记录头是 8 字节，依次为 little-endian `uint16 payload_length / type / mode / random`。type==2 时头部不执行这一层额外反馈编码；其他 type 的 8 字节头使用 byte key 反馈编码。此处的“未额外编码”不等于 TCP 明文：初始服务端记录在进入该函数前还经过上一节的连续流层。payload mode0 使用反馈编码；mode1 的整 16 字节前缀使用块算法，剩余尾部单独进行反馈编码，mode 其他值走复制分支。[B6]

块原语的静态证据与 AES 对应：128/192/256 位 key 分支、10/12/14 轮、GF 多项式约简 `0x1b`、仿射常量 `0x63`、S-box/逆表及轮变换。`0x10018598c` / `0x100185ba4` 包装器每次先清零 context；mode1 的每个明文块先异或上一密文块，首块使用零 IV，符合 CBC。记录路径传入 16 字节 key，因此是 AES-128-CBC 的静态识别；只处理整块前缀，没有在该记录包装处看到 PKCS#7 填充。主任务随后用原 `0x10018598c` 的双块合成输入做 Unicorn 离线执行，逐字节匹配标准 AES-CBC 零IV；另外回传两组已授权首响应的 outer(type2/mode1) → inner(type9/mode0) 解码及长度边界精确闭合。子任务未读取这些真实样本。该证据支持首响应记录的解密，尚不证明后续认证完成。[V4：主任务合成向量及首响应离线验证回传][B6；标准对照：[FIPS 197](https://csrc.nist.gov/pubs/fips/197/final)、[SP 800-38A](https://csrc.nist.gov/pubs/sp/800/38/a/final)]

## 7. 完整认证和读取账户的验收边界

`0x10013d974` 返回后，上层继续执行 `0x100038e58 → 0x10003cc30`：发送 command `0x10`，读取服务端状态，要求为 0，随后读取服务器配置。再执行 command `0x08`（`0x10003d420`）、command `0x0a`（`0x10003d630`）等初始化交换。[B7]

`0x100038f18 → 0x10003d7e8` 继续构造 command `0x1e`，经会话发送后读状态 0，接收至少 `0x3600` 字节的配置主体，再处理 224 字节记录数组并更新账户相关对象。这说明协议流程远超 C28/S首响应。command 的正式厂商名称、完整结构字段和订单/历史含义尚未核验，不能将这里的数组直接命名为持仓或历史订单。[B7]

### 7.1 return0 与服务器确认不是同一事件

`0x10013ca50` 只是把返回值置0并退出。正常路径由 `0x10013cf04` 调用 `0x10013d974`，在 raw-write 成功后跳到此处；另一个连接 mode==1 的特殊分支可更早直接到此处。正常路径在该 return0 前没有对 `0x18` 读取单独的服务端认证确认，因此上层“login”日志不能单独当作认证完成。[B4–B5, B7]

紧随其后的 `0x10003cc30` 对 command0x10 的响应处理有明确边界：[B7]

1. 通过连续流 helper 发送1字节 command0x10。
2. `0x10003cca0` 经 `0x1000376c0` 读第1个**流解码**状态字节，要求0，否则退出失败。
3. `0x10003cd00` 再读第2个流解码字节到 w22；后续按零/非零转为配置 flag，不能把它误当长度首字节。
4. `0x100037454` 读 `LE32(uncompressedLength)`，该调用上限65535；非零时继续读 `LE32(compressedLength)` 和压缩体，压缩长度要求1..131070，调用 `0x1000256f0` 解压并核对实际输出长度。长度0时返回空体，后续配置解析仍有自己的最低长度检查。
5. 解析服务端配置、接入点数组及字符串范围，完整通过才进入下一阶段。压缩块在下节确认是原始 LZO1X；配置字段正式含义继续单独核验。

所以 PoC 不能只记录“0x18发送成功”或任意一个解码零字节。更可靠的最小服务器接受证据是：按持续状态解码的 command0x10 状态0，加上同一响应的额外字节、长度/解压及配置结构验证通过；其后账户结构读取还须单独验收。此处是客户端控制流所要求的接受证据，尚未声称 Go 已做到。[B7]

### 7.2 command0x10 压缩体：原始 LZO1X

`0x100037454` 先通过持续流读取并解码长度和压缩体，再调用 `0x1000256f0..0x100025a78`。后者不是 zlib/deflate/gzip：末尾强制匹配 `0x11 0x00 0x00`，首字节>17按 `first-17` 复制literal，token分别按>=64、>=32、>=16分支，出现2049/16384距离区间、255增量长度扩展及 `ip[-2]&3` 尾随literal。这些路径逐项对应原始 LZO1X 的 M1–M4 格式。[B7；追加静态来源：`0x1000256f0`；一手格式说明：[Linux LZO stream format](https://docs.kernel.org/staging/lzo.html)]

该函数的 ABI 可规范为 `bool Decode(this_unused, src, uint32 compressedLen, dst, uint32* outputLen)`：输入的 `*outputLen` 是输出容量，实际输出字节数成功时写回；至少需要3字节输入，要求结尾标记及输入精确耗尽，并检查回溯源不早于输出起点、输出不超容量。`0x100037454` 还要求实际输出长度严格等于此前声明的未压缩长度。这里没有 lzop 文件容器头、zlib wrapper 或 LZO-RLE 版本头处理；直接将已经过持续流解码的压缩体交给原始块 decoder。[B7]

**[M4] 合成格式验证**：在已有离线 Core 中执行原 `0x1000256f0`，8组纯literal块（输出长度0/1/3/4/17/238/239/300）及1组 M2 重叠回溯均精确产生预期输出；截断、追加垃圾和输出容量不足3个合成反例均拒绝。未读取真实压缩体，也未执行网络登录。该证据与静态特征一起支持 LZO1X 识别，不只是以结束字节猜名称。

可供主任务直接选用的纯 Go 实现为 **`github.com/anchore/go-lzo`**，本次固定核验 commit **`c6cb39a30b970a032659a16015a86d1eb6ffd666`**（提交日期2026-10-30）。其实现只导入Go标准包，`go.mod`要求Go1.24.0，API为 `Decompress(src,dst) (outSize,error)`，使用调用者提供的输出缓冲区；源码检查输入、输出、回溯边界，并拒绝未耗尽输入。接入时分配已受上限约束的声明长度，要求 `err==nil && outSize==声明长度`。本子任务只审阅源码，未修改或安装该依赖。[固定源码](https://github.com/anchore/go-lzo/blob/c6cb39a30b970a032659a16015a86d1eb6ffd666/decompress.go)、[go.mod](https://github.com/anchore/go-lzo/blob/c6cb39a30b970a032659a16015a86d1eb6ffd666/go.mod)

该 commit 的 `LICENSE` 明确为 **MIT**，版权方 Anchore；实现文件注明依据 Linux 格式说明和 MIT 的 lzokay 实现。选择该包不需要从厂商反汇编复制解压代码，也不依赖原生C库。采用或分发时保留其许可证和版权声明；包与真实 MT4 压缩体的兼容结果仍由主任务在私有环境核对。[MIT LICENSE](https://github.com/anchore/go-lzo/blob/c6cb39a30b970a032659a16015a86d1eb6ffd666/LICENSE)、[实现出处](https://github.com/anchore/go-lzo/blob/c6cb39a30b970a032659a16015a86d1eb6ffd666/decompress.go#L1)

### 7.3 command0x10 配置的最低语义边界

`0x10003cc30` 对 LZO 输出的实际结构要求为 **`196 + 160*N` 字节**，N>=0：首4字节为两个LE16字段，随后是每项160字节的接入点记录，最后是64字节服务器窄字符字符串和128字节附加窄字符字符串。函数逐项检查可用范围，最终要求长度精确耗尽；两个LE16分别存入连接 `+0x70/+0x72`。这些记录属于连接配置，不能把它们视为账户、订单或已确认的独立 IP 所有权。[B7：`0x10003cc30..0x10003d134`]

普通路径还调用 `0x10003d134` 核对期望服务器名与返回字符串。精确位置为：尾64B从`4+160*N = outputLen-192`开始，尾128B从`outputLen-128`开始；程序分别强制其最后1字节NUL。从LZO输出到比较之间没有额外FE/AES/解混。**尾64B为char[64]，不是UTF16**：函数以格式`%s`读取它；另以`%S`读取本地配置`+0x39a4`的UTF16名字（所选服务器记录`+0x1ac`）。两边转NSString、按`-`分割，取第一段做不区分大小写比较。两边首段均非空且不等时返回失败并触发“连接到不同服务器”的错误；任一首段为空时，该原函数返回成功。[B7：`0x10003ce8c..0x10003cf0c`、`0x10003d134`；静态格式常量`0x10025d958/0x10025e238/0x10025fb78`]

该比较仅在本地配置`+0x3c8c==0`时执行。此flag不能从服务器status0推导：`0x1000377b8`加载已存账户时，在按服务器hash、按名字查目录均失败后，才调用`0x10002dae0`按地址及名称前缀寻找备用记录；成功后置flag=1。正常UI Connect路径`0x100037a38`先清零配置`+0x3c0c`起0xa8B，其中包含该flag。因此不能为获得成功而人工开启绕过。该检查既不是完整名称逐字节相等，也不是服务器身份密码学验证；PoC应把非空名称前缀比较、是否满足真实客户端绕过条件、配置结构解析分别记录。[B1, B7]

**[V6] 名称提取问题已解**：主任务修正char[64]误按UTF16提取的问题后，回传两组已捕获C28/C18逐字节匹配、LZO结构和非空broker前缀均匹配；再以新生成的有效安装材料I建立新Go连接，两组目标均通过0x10 status0、LZO结构及非空名称前缀验证，未开启绕过flag或放宽比较。此前“找不到前缀”的观察不再作为协议反证。主任务另纠正其原LZO离线oracle曾误用4参的调用，正确ABI含this共5参；由错误调用产生的全零输出观察作废，不影响M4使用正确ABI的合成验证。此时可记录服务器已接受会话到配置阶段；账户0x1e仍须另外验证，`authentication_verified`尚未据此置true。[V6：主任务会话回传，子任务未访问样本]

**[V5] 主任务另行回传的验证进度**：两组真实服务连接已能接收纯Go新生成的首段并正确解码首次响应；已捕获的0x18全部子记录可解包，type1标准SHA-1和安装材料首字节校验匹配；后续0x10的解码status为0、压缩块边界可读。子任务没有读取这些样本；截至该回传时，LZO解压、完整配置及账户字段的在线验证仍需主任务完成。此处不把新首段有响应或0x18离线一致升级为完整认证成功。[V5：主任务会话回传；B7]

### 7.4 command0x08、0x0a 和中间初始化命令

以下请求/回包都经 `0x1000373ec/0x100037378` 的**同一方向连续流状态**，使用挑战后Kc；命令之间不能重置RX/TX。顺序由 `0x100038e58` 给出：[B6–B7]

| 命令 | 发送的流层明文 | 必须消费的回包与边界 |
|---|---|---|
| `0x08` | 命令1B + 本地品种配置摘要16B | status1直接成功、无体；status0再读同一LZO块，上限`1936*65535`，解析要求非空且输出长度是1936的整数倍；其他status失败 |
| `0x0a` | 命令1B + 本地第二组配置摘要16B | status1无体；status0再读LZO，上限`80*65535`，解析要求非空且长度是80的整数倍；其他status失败 |
| `0x21` | 只有命令1B | 仅status0分支继续读LE32 N（1..1024）及N*68B，**不经LZO**；任何非零status都立即返回false，不读N/体，外层忽略该返回值并继续 |
| `0x22`（有条件） | 命令1B + LE32(start) + LE32(end) | 只有本地两个时间值非负且start<end才发送；status1无体；status0读LZO，上限128MiB，保存为224B元素数组；其他status失败 |

0x08的摘要getter `0x100042940` 优先使用已有非零16B摘要，否则以现有配置数组原始字节求MD5；没有数组时输出16个零。0x0a对应getter为 `0x100042ef4`，同样有无缓存的全零分支。这里的全零摘要是客户端已存在的首次同步请求路径，不代表可以在status1后凭空补全配置。0x08实际解析器 `0x100042b44` 使用0x790=1936B记录，静态日志source为“Symbols”，并记录“symbols synchronized”，故品种配置语义有直接程序证据。0x0a的80B结构暂只称第二组配置，尚未给字段正式命名。[B7；追加静态来源：上述getter/parser及`0x100042e00`]

0x21由 `0x10003ed70` 处理，`0x10003ee10`的`cbnz`使任何非零status立即返回false、没有N或体；外层`0x100038ecc`没有检查返回值，继续后续初始化。因此status1只消费该1B并继续，不能把它当成N的第1字节；也不能忽略已发送命令的status或流计数。主任务已回传两组status1与后续22/1e流边界精确闭合。[V7：主任务回传] 0x22由 `0x10003e868` 处理，日志明确为按时间段同步“history orders”；它可作为后续历史订单读取入口，但时间单位、完整224B字段、分页/更新规则仍需另验。初始本地没有有效时间区间时该函数不会发送0x22。此处仅确认官方客户端的顺序和条件，尚未证明服务器要求0x1e之前必须发送每一条可选命令。[B7]

### 7.5 command0x1e 的精确请求与账户回包

`0x100038f18 → 0x10003d7e8` 在前述初始化之后执行账户同步。流层明文按顺序为：`0x1e || LE32(flags) || prefix72 || optionalExtension`。[B7]

- 普通连接flags取决于 `news_enabled`：开启为0，关闭为2。调用者附加模式非零且连接mode==0时改为3；不能把这个flags直接命名为交易权限。
- `prefix72 = LE64(localState) || LE32(2) || zero[60]`，由 `0x10003dd94` 构造。localState来自 `0x10016c21c(core+0x10518)`，函数加锁读取对象`+0x10c`的uint64；其业务含义尚未证实，也未读取真实值。候选客户端使用0是否被服务端接受须实际验证，不能把它误作账号。
- 服务端build>=1362且连接mode!=1时，追加原始嵌套记录：外头`header8(type2,mode0,random0,length=8+S)`，内头`header8(type13,mode0,random0,length=S)`，主体为元数据字符串的UTF16LE及末尾NUL16，S=2×UTF16代码单元数+2，包含这个终止符。扩展整体长度为16+S，整个请求长度为93+S（无扩展时77B）；native以uint16写入头长度，独立实现应先限制S+8<=65535，避免截断。此处**不额外调用记录FE/AES包装**，只随整个0x1e请求进入连续流编码。
- type13生成链 `0x10013e86c → 0x10005b11c` 组装客户端元数据，键包含`package/devid/file/version/os_ver/computer`，每项格式为`key=value\t`，TAB分隔；遍历顺序不应推定为规范排序。空元数据生成失败，会阻止该请求发送。可提出使用自有客户端真实元数据的兼容候选，不应复制真实设备标识，也尚不能承诺服务器接受任意替代值。[B7；追加静态来源：`0x10003dd94`、`0x10013e86c`、`0x10005b11c`、`0x10016c21c`]

元数据键的值源头已逐项复核；`devid`是程序逐字节构造的5字节ASCII键，不能写成`device`。`0x10005b77c`只在value和key对象非nil时插入字典，因此“存在生成路径”不等于每个客户端必有全部六项，也没有确认服务端允许任意省略。[B9]

| 键 | 本程序的静态来源 |
|---|---|
| `package` | 可执行映像代码签名entitlements中的`application-identifier`，去首尾空白 |
| `devid` | 同一entitlements的`com.apple.developer.team-identifier`，去首尾空白；**不是硬件设备ID** |
| `file` | `NSProcessInfo.arguments.firstObject.lastPathComponent` |
| `version` | `CFBundleShortVersionString`按`.`分割，恰三段才取第三段，否则nil不插入 |
| `os_ver` | `UIDevice.systemName + " " + UIDevice.systemVersion` |
| `computer` | `UIDevice.name`；受平台版本条件分支抑制时nil不插入 |

`0x1000d0808`通过Mach-O的`LC_CODE_SIGNATURE`定位嵌入SuperBlob/entitlements，`0x1000d0924`以`propertyListWithData`解析静态属性；没有向服务器或设备查询应用签名值的网络步骤。本研究未记录其实际AppID、team或设备名。该程序确实读取签名元数据，不能再说“未见签名处理”；**type13本身只发送上述字符串，未见把签名证书/签名blob作为type13主体发送**。服务器如何验证这些值仍未知。自有profile超时与字段校验之间目前只是假设，不能凭超时就定为元数据被拒。[B9；Mach-O定义：[Apple loader.h](https://github.com/apple-oss-distributions/xnu/blob/main/EXTERNAL_HEADERS/mach-o/loader.h)]

0x3d7e8前段另生成16B伪随机材料并计算MD5/反馈编码，存到连接`+0x90`；构造正式请求前会清空临时发送缓冲区，因此该r16和build不是独立发送字段。它不改变持续流helper使用的Kc，不能擅自添加到上述请求布局。[B7]

回包要求流解码status为0，然后调用相同LZO块读取器，上限64MiB，解压输出必须**至少0x3600=13824B**。前13824B由 `0x1000288fc` 映射到 `AccountInfoBase`；此后每个完整224B追加到交易订单数组。日志明确为“trade orders synchronized”，但当前未把这224B结构的订单种类/完整字段还原；不足224B的尾部在该官方函数里未显式拒绝，PoC须单列剩余字节，不能默默称作完整解析成功。[B7–B8]

### 7.6 账户字段的最小可验收语义

下表偏移均相对 **0x1e解压输出起点**，不含status、长度或LZO体；多字节数字在本arm64程序按little-endian读取。主体到`AccountInfoBase`的转换由 `0x1000288fc` 直接给出，再以UI文字或命名query字段交叉确认。[B8]

| 解压主体偏移 | 类型 | AccountInfoBase偏移 | 已确认的语义证据 |
|---|---|---|---|
| `0x44` | uint32 | `0x1a4` | 杠杆。`0x1001360dc`读取配置快照该字段，经numberWithInt/stringValue生成名为`leverage`的query项 |
| `0x48` | float64 | `0x1a8` | 余额。`0x1000aa3c0`的`Balance:`行读取该字段；另有名为`balance`的query项 |
| `0x50` | float64 | `0x1b8` | 信用。相同UI函数的`Credit:`行读取该字段 |
| `0x35d8` | uint32 | `0x1d8` | 投资者图标原始指示。`CCellCurrentAccount.AccountType:`为0时隐藏`_investor`，非0时显示；尚不足以独立判定真实交易权限 |
| `0x00` | uint32 | `0x118` | demo指示。相同方法在非零时选用`account_demo`图像；不能把它当成杠杆或交易权限位 |

映射时`raw+0x35d8`起8字节通过浮点寄存器搬运到base+0x1d8；搬运指令并不表示该8字节是double。UI实际读取前4字节为整数指示。后4字节和其他权限位当前未赋业务名称。`raw+0x58`起0x3580B另复制为组配置，该布局与13824B最低大小相互吻合。[B8]

当前**没有确认**0x1e主体中独立的服务器回显账号字段。AccountInfoBase的账号来自登录时的本地配置，不能把它当作服务器payload的账号回显证明。最小只读账户验收应记录：此登录会话的完整0x10配置、连续流状态、0x1e status0/LZO/最低结构边界均通过；余额/信用（按官方显示精度）、杠杆及投资者图标原始指示分别与官方客户端匹配；交易只读权限另行保留证据与验证状态。真实值只在私有环境内比较，长期报告只保留布尔和长度。未找到服务器账号回显之前，准确说法是“该账号登录会话读取的账户字段一致”。[B7–B8]

投资者图标指示的实际指令为`load uint32 → cmp 0 → cset(eq) → setHidden:`，未见位掩码、取反或额外解混。主任务回传一组已捕获0x1e解压主体13824B、余额信用为finite、订单尾0，但该原始指示为0，与用户对凭据类别的描述不一致。应保留原始指示、`read_only_verified=false/待核验`，不能强改为非零，也不能反向把0解释为已证实只读；更不能主动发送交易命令验证权限。该回传支持账户结构定位，尚非Go新会话账户读取成功。[V7：主任务回传；B8]

当前研究仍不覆盖所有交易权限组合、币种/保证金全部字段、历史范围完整性及断线增量恢复；下节仅追加224B记录中已有直接语义依据的字段。[B8–B9]

### 7.7 双连接与flags来源

0x1e的x2不是“普通启动固定为1”。在0x10之后，`0x100039288`把worker`+0x160`清0，按当前连接地址匹配160B接入点记录，读取匹配记录`+0x84`的uint32非零性；为1时启动mode1第二连接的两个有依赖关系的NSBlockOperation。第一块`0x100039b70`先执行第二连接C28握手，成功后还调用`0x100039f2c → 0x10003d7e8`在第二连接发0x1e；成功后把第二连接状态设4。主连接0x1e之前，`0x100038f18`先调用`0x1000395a8`等待第一块完成，若已取消或第二连接状态<4则清worker flag；最后才把worker`+0x160`传入x2。故flags3与第二连接成功状态有本地控制流依据，但还没有证明服务端必需依赖它。[B7, B9]

mode1短握手使用程序静态常量字符串`0x10023c2ad`的MD5，替代普通用户密码摘要；C28首字节为11、末flag为0。服务端raw status之后，只连续流解码extra1/build2/F4（因此形状可为C28→S8）；检查有符号build>1419后直接return0，不读64B挑战、不派生普通Kc、不发0x18。第二连接的后续0x1e仍以这个MD5作为连续流key，RX已消费7B、TX从0；mode1不加type13，flags按news设置为0/2。原客户端不把C28→S8本身当成第二连接完整账户同步成功。[B4, B9]

prefix72的localState具有明确冷初始化0路径：`core构造0x100032e40 → 0x10016a5c0 → 0x10016a388 → 对象+8的0x10016d3a0 → 0x100029d54 → 对象+0x28的0x1000289d4`，最后bzero 0x2e4覆盖getter读的对象+0x10c。后续`0x10016ade4`才把新记录的uint64写入该字段。其业务语义尚只推测为消息/新闻同步游标；没有证据要求先有账户数据或填入非零值。主任务两组原客户端prefix72均为零，与该初始化路径一致。[B9；追加静态来源：上述初始化/setter；V7]

**[V8] 主任务新Go会话进度**：以自有type13 profile发送0x1e，两组目标均在等第1个响应status时超时；单独将flags2改3仍超时。另一个新Go会话在加入0x22后，已收到status0、LZO及整224B历史订单数据，但0x1e仍超时。该结果支持会话已足以执行历史读取，并不证明账户同步完成；元数据兼容、双连接及其他会话差异仍按独立假设处理。子任务未读取任何真实值或样本。[V8：主任务会话回传]

**[V9] 元数据组的后续实证**：主任务保持新生成安装I、uniqueUserNumber=0、不建立第二连接，仅将type13整组自有profile换成公开移动端1478兼容profile后，单个目标的新Go连接依次通过0x10/08/0a/21/22/1e，账户输出满足`13824+15*224`且尾数0、投资者图标原始指示非零，并读到指定两日范围的历史订单。此结果证明该配置下单连接可以完成账户同步；**只支持整组元数据改变与成功相关，尚未隔离package/devid/file/version/os_ver中哪个字段是必要条件**，也未证明省略字段的接受规则。flags2与3的差别、另一目标和UI金额/时间核对由主任务继续验证；本子任务未读取这些真实值。此前V8超时不能再作为“单连接一定不可用”的依据。[V9：主任务会话回传]

### 7.8 224B TradeRecord的可用字段

ObjC元数据把交易和历史cell的Update参数直接声明为`TradeRecord`；其字段类型顺序按arm64 ABI合计224B，与0x1e/0x22的数组步长一致。0x1e订单通过`0x1000a171c`赋给交易数组，0x22通过`0x1000a23e0`赋给历史数组；这些入口原样Assign，随后仅建立排序指针，未在这里交换字段。[B7, B9]

以下偏移相对单条224B记录起点，数字均little-endian；只列有直接显示或具名ivar证据的字段：

| 偏移 | 类型 | 已确认的使用 |
|---|---|---|
| `0x00` | int32 | 订单号，按`#%d`显示 |
| `0x08` | char[12] | 品种，交给品种字符串解析/显示 |
| `0x14` | int32 | 价格小数位，作为`FormatPrice`的Digits参数 |
| `0x18` | int32 | 操作类型，`0x1000a285c`按表`0x1002562a0`取字符串 |
| `0x1c` | int32 | 数量，UI除以100显示手数 |
| `0x20` | int32 | 时间A，传入`FormatDateTime`；见下文命名边界 |
| `0x28` | float64 | 第一价格，历史表第一Price列 |
| `0x30` | float64 | 止损，写`m_sl` |
| `0x38` | float64 | 止盈，写`m_tp` |
| `0x40` | int32 | 时间B，传入`FormatDateTime`；见下文命名边界 |
| `0x60` | float64 | commission，写`m_comm` |
| `0x70` | float64 | swap，写`m_swap` |
| `0x78` | float64 | 第二价格，历史表第二Price列；当前交易列表也使用此字段 |
| `0x80` | float64 | profit，`FormatMoney`后写`m_profit` |
| `0x88` | float64 | taxes，写`m_taxes` |
| `0x94` | char[32] | 备注，历史展开行与时间拼接显示 |

操作类型表精确为0=buy、1=sell、2=buy limit、3=sell limit、4=buy stop、5=sell stop、6=balance、7=credit；超出0..7返回空字符串。0x1e的0/1可作为持仓记录候选、2..5为挂单、6/7为账务类型，但历史流同样有buy/sell，不能脱离命令来源和关闭状态一概命名为当前持仓。当前尚未定义所有state/activation/网关扩展字段。[B9]

**时间命名边界**：`CTradeDealSelCell.Update:`对当前交易展开行使用时间A；`CHistoryCell`对时间A的目标ivar名为`m_close_date`，而`CHistorySelCell`在展开行使用时间B。另一方面，iPad历史表`0x10018f08c/0x1001904b4`的列顺序是Order、时间A、Type、Size、Symbol、第一Price、S/L、T/P、时间B、第二Price，吻合官方文档定义的开仓时间/价格在前、平仓时间/价格在后。**由这些证据推断**A为开仓、B为平仓（第一/第二Price相应为开/平仓价格），但单独依赖m_close_date这个名字会得出相反结论，仍须主任务用官方UI的已知历史条目私下交叉核验后再把推断升级为已验证。时间单位/时区也未仅凭字段类型定为UTC。[B9；官方界面定义：[MT4 Account History](https://www.metatrader4.com/en/trading-platform/help/overview/terminal/terminal_account_history)]

后续验证应分层记录，至少满足：

- 用合成账号/密码做 C28 生成与逆混淆检查，字段、长度和端序逐项一致；真实材料仅在用户已授权的私有验证环境内比较，不进入报告。
- 对已授权首响应先复现原始状态及连续流解码，再复现状态分支、挑战算子、8 字节头和记录解码；正确边界和长度是必要检查，但不能单独证明 key 正确。
- 对后续 `0x18` 请求复现子记录顺序、type3 的 key 演化和外层编码；发送完成仅记为发送完成。
- 取得下一次实际服务端响应并解析 status/配置，确认会话材料持续可用；认证完成的判断须有该响应的语义证据。
- 单独实现并验证账户、持仓和历史的结构/请求、时间边界、更新及断线恢复；本轮静态认证研究没有完成这些功能。

## 9. 白天验收的补充与语义更正

2026-11-11 白天新增的[只读验收记录](mt4-readonly-acceptance.md)补齐了三家实测、币种/净值/保证金、订单时间与价格语义以及历史分窗重查。前述未决项保留为历史阶段记录，当前范围以新版报告为准。

## 8. 主任务最终集成验证回传

主任务已将上述协议观察独立实现为[纯 Go PoC](../../packages/mt4/README.md)，并完成[真实验证](mt4-native-validation.md)：DLSMarkets、DPrime 均在 macOS arm64 和 Linux arm64 的独立 TCP 会话中，通过首段、C18、配置、账户与历史同步；单连接flags2即可，无须运行参考客户端或建立其secondary线程。Linux运行环境由scratch构建，仅含静态Go文件。新安装随机材料和用户编号0可用，元数据使用公开移动端兼容标识，未复制真实硬件或用户材料。
