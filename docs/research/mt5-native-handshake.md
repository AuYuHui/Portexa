# MT5 原生握手研究

前序研究离线分析了第三方厂商 MTAPI 公开发布的 Linux x64 试用程序集 `mt5api.dll`，并用合成数据验证传输层解析。受检程序集的 SHA-256 为 `01c93aea0d7c698bbd9e2b8a3415e0b044b23c04f9974db9fae22bf50ab9f734`。 [MTAPI 试用程序集](https://reg.mtapi.io/root/mt5rest-trial/-/blob/a823b370242a6af8a1799759910c832b1e2e8229/trial-linux-x64/mt5api.dll)

## 静态证据

- `OutBuf.CreateHeader` 与原生接收解析器使用相同的 9 字节帧头。依次是消息类型 `uint8`、载荷长度 `uint32`、序列号 `uint16` 和标志位 `uint16`，多字节字段均为小端。接收侧以最低位识别压缩，以次低位识别最后一个分片。登录后的回复按序列号关联，接收侧同时检查消息类型。 [MTAPI 试用程序集](https://reg.mtapi.io/root/mt5rest-trial/-/blob/a823b370242a6af8a1799759910c832b1e2e8229/trial-linux-x64/mt5api.dll)
- 压缩分片先读两个小端 `uint32`，分别为解压后长度和压缩数据长度，再读压缩块。解压函数的结束标记、字面量复制和回引用规则与 LZO1X 一致。 [MTAPI 试用程序集](https://reg.mtapi.io/root/mt5rest-trial/-/blob/a823b370242a6af8a1799759910c832b1e2e8229/trial-linux-x64/mt5api.dll) · [Linux 内核 LZO 解码说明](https://docs.kernel.org/staging/lzo.html)
- 该 SDK 在前置交换后分别初始化入站和出站流状态，再继续授权和同步。其静态调用链包含对 MTAPI 服务的依赖，证据范围限于本试用程序集。 [MTAPI 试用程序集](https://reg.mtapi.io/root/mt5rest-trial/-/blob/a823b370242a6af8a1799759910c832b1e2e8229/trial-linux-x64/mt5api.dll)

## 官方客户端 build 6300

macOS 上运行的 ARM64 终端与应用包里的可执行文件 SHA-256 一致，均为 `02b9f6103789bc652eb179264e99d8697b2a33d97ed6f06dabef3e83fc28a161`。以下为该样本的未重定位虚拟地址，供复核用。

| 阶段 | 证据 |
| --- | --- |
| 帧解析 | `0x100129a0c` 累积 9 字节帧头，使用第 1 字节偏移处的小端 `uint32` 作为载荷长度。`0x100129c44`、`0x100129c88`、`0x100129ccc` 分别读取类型、序列号和标志。`0x10016559c` 用类型和序列号归并分片，并检查标志的次低位决定是否结束。 |
| 初始交换 | 多个握手响应处理函数调用 `0x100300b28`，只转换帧头后的载荷。每次调用使用初值零，以前一个密文字节和固定的 16 项循环表逐字节解码。 |
| 认证响应 | `0x100113dec` 先解码载荷，再读取固定区和扩展字段。对于送入流状态初始化的扩展字段，读取方式是一个字节的类型、四字节小端长度和对应字节串。固定区中的能力位选择 16 或 32 字节证明校验路径。 |
| 状态切换 | `0x1001175f8` 的 32 字节路径先比较 `SHA-256(基础摘要 ∥ 客户端挑战)` 和响应中的证明。`0x100117dd0` 将有效账户标识的 8 字节小端值、UTF-16LE 口令和固定上下文字符串顺序送入 SHA-256，无终止符。证明匹配时，`0x100112114` 用基础摘要和响应固定区偏移 `0xE0` 处的 256 字节初始化载荷表。构表逐块执行 AES 加密，每块先与上一块的输出异或，初值为全零。 |
| 后续接收 | `0x100165418` 按连接状态选解码路径，保持原帧头。256 字节表模式下，`0x100165838` 为标志最低位有无置位分别执行不同的载荷转换，状态会跨帧更新。最低位置位的载荷需要先走对应转换，再交给上层。 |

使用隔离的 ARM64 仿真执行上述样本中的局部函数。所有输入均为合成数据。初始解码 7 例、AES 构表对照 OpenSSL 8 例、SHA-256 对照标准库 6 例、两组消息类型中的接收转换 18 例均通过。单独验证基础摘要 6 例，覆盖两种内部账户标识选择和三种 Unicode 口令。认证切换的 4 例分别覆盖证明和材料有效、证明不匹配、材料缺失、材料长度超限。另有两例从合成账户标识和口令直接走通摘要生成、证明校验、状态初始化及连续两帧解码，仿真只替代字符串容器和帧缓冲访问等外部依赖。

## 原生登录实测

使用投资者凭据，在当前终端的接入点上复测。服务器先要求切换握手并报告 build 6230，随后对 128 字节扩展请求返回有效挑战。独立探针提交 268 字节的认证正文，内含基于服务器挑战生成的两种证明和新生成的客户端挑战。服务器返回成功状态，并用握手能力位选择 SHA-256。探针用本次客户端挑战验证了服务端证明。采用标准库的独立 [研究探针](../../research/mt5-handshake/probe.py) 复测得到相同结果。

报文类型、升级状态及最低版本集中在 `WireProfile` 中。握手按当前阶段和序列号核对回包，证明格式由回包能力位选择。测试替换了三种消息类型以及升级状态，覆盖错误序列、错误证明、未知版本和截断扩展字段。线上兼容性仅确认了本次观察到的握手变体。

官方客户端通过证明校验后，会调用 `0x100074cb0` 构造初始同步。试验按 `0x1001337e0` 补入冷启动同步字段，并在隔离仿真中计算该会话返回的附加材料对应的确认值。发送前确认连接仍开放，发出同步请求后收到 EOF。本次仍缺有效的同步请求组合和同步响应，因此无法独立验证服务端权限位，也没有获得供看板对账的账户快照和历史。

## 首次同步对照

- 追踪 `0x1001337e0` 至 `CheckCreateUniqueUserNumber`，确认官方终端会发送本地生成的 64 位安装实例编号。低 32 位以 2015-01-01 UTC 为纪元。本轮补齐该字段，使用合成安装编号、摘要和会话确认值执行官方函数，四组冷缓存载荷与独立编码逐字节相同。字节对照限定在合成的空缓存状态。
- 对 `0x100192668` 的隔离调用确认，发送状态为零时原样保留帧，已安装滚动表时只转换载荷。此前探针因可选扩展缺失而按零状态发送。官方重连样本确认本分支实际从固定区生成滚动表。
- 原生探针再次完成 SHA-256 双向认证。发送补齐实例编号的同步请求后收到 EOF，修正实例编号的纪元后结果相同。独立对照会话仅发送一个空保活帧，保持连接至 8 秒读期限，未收到响应。当前已复现的触发点是首次同步请求，实际终端的动态字段、会话选择与关闭原因仍待线上样本确认。
- 官方客户端 `0x1001ccd08` 在权限掩码包含 `0x08` 时走 `investor mode` 分支。第三方 SDK 的 `get_IsInvestor` 也检查账户记录的 `TradeFlags & 0x08`。另一个状态位 `0x04` 表示服务器禁止交易。原生 TCP 对账仍需从同步响应取到账户记录、核对账号及确认投资者位。 [MTAPI 试用程序集](https://reg.mtapi.io/root/mt5rest-trial/-/blob/a823b370242a6af8a1799759910c832b1e2e8229/trial-linux-x64/mt5api.dll)

## 官方重连样本

- 本机管理员授权后，限定到官方 MT5 进程捕获了一次成功重连。将双向 TCP 流按序重组，先验证官方挑战和服务端证明，再从认证响应固定区构建滚动表。官方编译样本 `0x100114534` 将固定区传入 `0x1001175f8`，对应可选扩展缺失时仍须转换发送载荷。线上样本解码后，重新编码的客户端载荷逐帧与捕获字节一致。
- 收到的 354 个认证后帧均完成载荷转换，压缩帧完成 LZO 解压。首次同步响应由六帧组成，从账户记录确认了同一账号的投资者权限，余额和信用与官方终端一致。本样本的 `0x66` 历史帧是按品种请求的行情历史，逐笔成交、挂单和出入金仍缺全量对账证据。
- 成功的官方请求带有安装实例编号、缓存状态、客户端选项和会话确认值。用本次官方握手输入重新计算的会话确认值与抓包一致。独立探针切换到该滚动表后，尝试常规冷缓存请求以及填入自身客户端标识的请求，服务器仍在首次同步后关闭连接。账务字段目前仅能从官方终端的成功样本中验证。

## 首次同步差异复测

使用已保存的官方成功样本作基准。本轮重新解码该样本，并在同一接入点发起独立实测。样本中官方终端在收到认证回复 20.7 毫秒后发出首次同步，152.2 毫秒后收到第一帧响应。独立探针的认证状态、能力位、固定区长度和扩展结构均与样本匹配。发送端和接收端分别使用独立滚动状态，客户端载荷仍可离线逐帧还原为捕获字节。

| 官方请求顺序 | 字段对照 |
| --- | --- |
| `0x22`, `0x6C` | 同步选项掩码一致；安装实例编号按各自会话使用本地值。 |
| `0x16`, `0x18`, `0x84` | 官方样本开启资讯同步，后两个字段与空缓存探针一致。 |
| `0x7F` | UTF-16LE 客户端声明，使用制表符分隔并以零字符结尾。包含包名、系统、签名团队、可执行文件名和版本。官方样本的 `devid` 与安装应用的代码签名 Team ID 一致，`package` 包含应用标识。 |
| `0x07`, `0x28`, `0x11` | 官方样本报告 48 条品种缓存，另两项与空缓存探针一致。 |
| `0x58` | 放在末尾。使用每次认证的材料计算会话确认值。使用录制会话的原始输入离线计算，结果与捕获的确认值一致。 |

将录制会话的对应字段值用于离线编码时，完整同步载荷逐字节匹配官方请求。独立连接将首次同步提前到认证后 19.2 毫秒，仍收到 EOF。在保留独立客户端声明的情况下单独对照官方品种缓存摘要，结果相同。本机 Portexa 二进制没有签名团队，省略 `devid` 的实测也收到 EOF。服务器没有返回可解码的拒绝原因。客户端声明仍是可观察到的差异，现有证据无法确认服务端是否使用它作准入判断。研究编码器已补齐声明序列化和字段顺序的合成回归，尚未得到独立只读快照。

## 独立 TCP 连接上的扩展认证

按 TCP 连接分别重组已保存的官方样本。官方终端在新的连接上直接发送扩展挑战，再提交证明和首次同步。样本中较早的初始交换使用另一条短连接，与后续扩展认证各有独立的 TCP 序列。之前的探针把旧式协商和扩展认证放在同一条连接上。

探针新增 `--direct-extended` 选项。直接分支读取扩展挑战返回的服务器版本，仍校验服务器证明。消息类型继续由 `WireProfile` 提供。使用已授权的投资者账户，在录制样本对应的接入点实测一次，服务端返回 build 6230，SHA-256 证明通过。该探针在验证证明后关闭连接。本次实测覆盖直接认证阶段，尚未验证该分支的独立首次同步。

对同一历史抓包重新验证服务端证明并解码同步响应，识别出计数与实际行数一致的一组 672 字节持仓记录。后续已解码的历史请求为行情请求。挂单和逐笔数据的完整性尚未核对。已登录终端当场生成的交易报告与历史页资金汇总一致。移动端提供汇总 PDF，当前经纪商的公开页面也尚未核实对应服务器的 Web 终端域名。 [MetaTrader 5 移动端交易报告](https://www.metatrader5.com/en/mobile-trading/iphone/help/trade/report) · [MetaTrader 5 Web 终端接入说明](https://www.metatrader5.com/en/trading-platform/web-trading/how-to-connect)

## 直接认证后的同步响应

在隔离环境中复核了官方捕获会话的确认值。使用重新认证返回的挑战和登录标识生成本次会话的确认值，以独立客户端声明和空缓存发送同步请求。三次有界线上测试均收到两个可正常解压、类型与序列匹配的响应分片，随后服务端关闭连接。三个连接均未收到最终分片。捕获的官方历史样本可用同一接收器重组为完整响应，最后一片带结束标志。

研究接收器新增对缺少最终分片、帧大小上限和不同序列交错的检查。它只交付有匹配结束帧的回复。服务端关闭连接的原因仍未知，独立会话尚未完整读取账户记录，也未确认该会话的投资者权限。

## 账户记录前的断线范围

使用同一接入点实测空缓存和已捕获的品种缓存摘要。空缓存返回两片，合并后的内容从品种目录区段开始，两片均未出现账户标识。带上该缓存摘要后，服务端返回一片，解压后与官方抓包的首片逐字节一致，随后断开。缓存摘要改变了目录回传量，两种探针均在账户区段开始前断开。摘要只用于对照试验。

官方终端的账户片在发送同步请求后约 157 毫秒完整到达，下一条客户端请求约在 168 毫秒发出。这份成功抓包里，收到第一片目录后，官方终端没有再发应用层请求便收到了账户片。清零探针中尚未初始化的认证状态字段和关闭资讯同步分别复测，结果均未改变。复用本地仿真环境后，直接路径的认证至同步发送间隔约 313 毫秒，仍长于官方样本的约 21 毫秒。本轮未控制到相同间隔，服务端也没有返回可解码的关闭原因。

## 约 21 毫秒的首次同步对照

在隔离子进程中加速本地会话确认值计算。用八组合成输入和保存的官方握手挑战与隔离仿真的输出逐项比对，结果均一致。EC Markets 同一投资者账户和同一接入点的下列实测，以读完认证回复至首次同步发包完成的本机计时为准。每次建立新连接并用本次挑战生成确认值。

| 同步请求条件 | 实测间隔 | 结果 |
| --- | ---: | --- |
| 品种缓存摘要，较慢对照 | 317.64 毫秒 | 一片品种目录后断开 |
| 同一份品种缓存摘要 | 21.10 毫秒 | 相同的一片品种目录后断开 |
| 空缓存 | 21.14 毫秒 | 两片品种目录后断开 |
| 品种缓存摘要，非零起始序列号 | 21.05 毫秒 | 相同的一片品种目录后断开 |

品种缓存摘要组的首片解压后与保存的官方首片逐字节一致。四组均未收到该账号的账户记录或结束帧。缩短间隔及改变起始序列号均未打通本次首次同步，无法验证独立会话的投资者权限。加速器与计时工具仅用于本机研究。

## 第二份官方重连与认证状态

重新抓到一份完整的官方登录、首次同步与后续查询。该会话使用了同一交易服务器的另一个接入点。同步请求仍申报已有品种缓存，认证请求中也带有保存的状态。同步响应六片齐全。从完整同步的 `0x25` 区段读取 2996 字节账户记录，已核对账号和投资者权限位。此前出现在区段附近的 `0x18` 在这两份样本里是一个计数为零的独立区段。抓包中后续 `0x65` 两个子请求均只有短回复，`0x66` 子类型 14 为行情历史。本样本尚不足以确认逐笔历史的数据覆盖。

官方终端在认证成功后，将固定回复偏移 `0x2e8` 的 8 字节交给状态保存回调，下一次生成认证证明时从同一回调取出状态，写入请求偏移 `0x68`。两份官方样本的已发状态和回发状态均非零，值随连接变化。研究探针保留经服务端证明校验的回复状态，调用方可以在同一账户、同一接入点的后续认证中带上它。

在原接入点对照了空状态和探针自己上一次认证取得的状态，两次均在返回首片品种目录后断开。新接入点的独立直连在扩展挑战前关闭，先做初始协商可通过 SHA-256 双向认证。随后在约 21 毫秒发起首次同步，使用新官方样本的品种缓存摘要并开启资讯。首次认证与带本次签发状态的重连都只收到与官方首片一致的目录，仍缺账户区段和结束帧。独立原生同步和 Portexa 对账仍待完成。

## 扩展请求编码与匿名目录对照

两份官方样本的 128 字节扩展请求都把第一个随机字节按有符号值扩展到 8 字节，构造函数 `0x100114ed0` 对应同一行为。研究探针已按该规则编码，并用正负边界值测试传统与扩展请求布局。修正后，在新接入点两种对照均直接完成 SHA-256 双向认证。此前该接入点出现的扩展挑战前断线未在本轮复现，单独原因仍未知。

两份样本中的短连接以空账号字段发起匿名协商，随后查询同一交易服务器的目录。结果由终端的目录回调处理。用新样本接入点在线复测，在独立短连接收到正确关联的两片成功目录回复，再开账户连接。保持约 21 毫秒、品种缓存摘要与资讯选项，比较有无该步骤，并复测省略客户端声明和带探针本次签发的重连状态。所有账户会话都只收到一片品种目录，解压后逐字节匹配官方首片，未得到账户区段和结束帧。这些实验尚未定位服务端关闭原因。

## 首片后的收发顺序

以各自样本发出首次同步请求为零点，对比 TCP 载荷覆盖完整应用帧的时刻。两份官方记录里，客户端均在完整收到同步结束帧后才发出下一条应用请求。第一片和第二片之间只观察到一个客户端裸 TCP ACK。

| 官方样本 | 首片收齐 | 账户分片收齐 | 同步结束帧收齐 | 下一条应用请求开始 |
| --- | ---: | ---: | ---: | ---: |
| 前一份重连 | 152.24 ms | 157.11 ms | 164.72 ms | 168.03 ms |
| 新接入点重连 | 111.46 ms | 128.79 ms | 130.78 ms | 133.63 ms |

在新接入点用独立探针按相同账户与约 21 毫秒间隔复测。启用套接字级的更频繁 TCP ACK 选项后，首片仍逐字节匹配官方，随即读到 EOF。套接字进入 `CLOSE_WAIT`，`SO_ERROR` 为零，说明收到了对端 TCP FIN。两份官方样本均没有要求在首片后发出的应用确认步骤。本轮实测未得到可解释对端关闭原因的应用错误，也未读到完整的账户记录。

## 首次同步前的认证对照

用同一投资者凭据离线复算两份官方重连样本的 MD5 兼容证明、SHA-256 客户端证明和 SHA-256 服务端证明，三项均逐字节匹配。在第二份样本的接入点新建一条独立连接，仅运行至双向证明通过。扩展挑战和认证回复均返回成功，服务器 build 6230，认证能力位为 `0x02`。回复中的两个扩展与两份官方样本逐字节匹配，独立连接也收到了新签发的 8 字节状态。

官方 268 字节证明正文随机初始化，再填入证明、客户端挑战和重连状态。两份样本的可选标志区域均为零，未附加认证扩展。固定回复偏移 `0x314` 的数据还有独立的派生状态，已追踪到首次同步之后的签名路径，首次同步构造器不读取这份状态。

两份官方扩展请求的末尾 80 字节都含非零字节，终端构造函数没有显式填充这一段。保持同一投资者账户、接入点、探针实例、同步选项和缓存对照条件，分别使用零填充和独立生成的合成填充发起同步。两组均通过双向认证，分别在认证后 21.06 和 21.05 毫秒发出同步请求，都收到一段与官方样本相同的品种目录，随后收到对端 FIN。两组均缺账户记录与结束帧，也没有返回协议错误码。这次对照未定位接入端关闭连接的具体原因。确认关闭原因需要接入端对应会话的日志或诊断码。

## iPhone 真机与 Mac 的认证和首次同步

使用 Mac 上的 RVI 对连接的 iPhone 做了 120 秒的抓包。经纪商接入点范围内捕获 1796 个包，包含三条可完整验证的 MT5 原生 TCP 会话。三条与最新 Mac 样本使用同一账户和接入点，均复算通过两种客户端证明和 SHA-256 服务端证明。服务端状态、能力位、两个扩展的内容，以及客户端模式、版本和认证正文长度均一致。手机后两条连接携带的 8 字节重连状态分别与上一条认证回复签发的状态一致。

每条手机会话在认证后 27.70 至 29.58 毫秒发出首次同步，确认值均可用已有算法复算。三条都收到六片，首片目录与 Mac 逐字节一致，账户记录中的账号和投资者权限位均通过核验。最新 Mac 样本以相同方式测得认证至同步间隔为 20.35 毫秒。先前保存的独立探针实测只收到目录，本轮没有重新登录独立探针。

| 首次同步字段 | 对照结果 |
| --- | --- |
| `0x58` 会话确认 | 每条连接按自身认证材料计算，手机、Mac 和探针均已验证这一计算路径。 |
| `0x6C` 安装实例 | 手机三条连接使用同一个编号，与 Mac 编号不同。两台官方终端的实测编号均超出探针采用的当前新建格式。Mac 二进制 `0x1000c7064` 是缺少既有编号时的生成路径，`0x1000c7210` 会直接取缓存编号或走本地读取路径。样本只能确认两个编号都被接入端接受。 |
| `0x7F` 客户端声明 | 手机与 Mac 的五个键一致，只有 `os_ver` 的值不同，二者均提供 `devid`。带相同品种缓存摘要的探针对照使用自身声明，未提供签名团队字段。 |

其余首次同步字段在 Mac 与手机间逐字节一致。真机样本没有展示额外的认证消息。安装实例和客户端声明仍是与独立探针的可观察差异，抓包无法确认接入端用哪项条件作出断开决定。

## 安装实例与客户端声明实测

重新验证三条 iPhone 样本和最新 Mac 样本的账户、投资者权限及首次同步。两个官方客户端的安装实例高 7 位不同，低 32 位按已知纪元解释都落在有效时间范围内。四个客户端声明键的值相同，包括签名团队字段，系统版本字段不同。已观察到的成功响应覆盖两种安装实例高位取值。

在同一账户和接入点，用探针自己的实例编号与客户端声明，保持品种缓存摘要、资讯设置和其余字段相同。初始对照不带重连状态，接下来的四次带上一条独立连接新签发的状态。所有连接都通过双向认证，在认证后 29.05 至 29.36 毫秒发送首次同步。

| 安装实例 `0x6C` | 客户端声明 `0x7F` | 结果 |
| --- | --- | --- |
| 探针生成 | Portexa 自身声明 | 一片品种目录后收到 FIN |
| 缺省 | Portexa 自身声明 | 一片品种目录后收到 FIN |
| 探针生成 | 缺省 | 一片品种目录后收到 FIN |
| 缺省 | 缺省 | 一片品种目录后收到 FIN |

五次目录均为 7370 字节，解压后逐字节匹配官方首片。另做一次探针实测，统计接收器收到的所有应用帧头，只读到这一片目录，未发现独立的错误或控制帧。实测覆盖字段有无和探针自有实例，未覆盖带真实 Portexa 签名团队字段的运行条件。本机没有可用的代码签名身份。仍缺接入端关闭原因，独立探针未读到账户区段和结束帧，未进入 Portexa 接入和对账。
